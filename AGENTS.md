# AGENTS.md

## Назначение проекта

Это Flutter-приложение с интерфейсом на Material 3. Кодекс должен сохранять
платформенную доступность, адаптивность и предсказуемое поведение интерфейса.

## Рабочий процесс

1. Перед изменениями прочитай `SKILLS.md`, `pubspec.yaml` и ближайшие правила в
   изменяемом каталоге.
2. Сначала найди существующие виджеты, тему, маршрутизацию и слой состояния.
   Не создавай второй механизм для той же задачи.
3. Делай небольшие изменения с понятным назначением. Сохраняй публичные API и
   формат данных, если задача явно не требует миграции.
4. После изменений запускай форматирование, статический анализ и подходящие
   тесты. Для UI дополнительно проверь светлую/тёмную тему и компактную ширину.
5. В финальном сообщении укажи изменённые файлы, проверки и оставшиеся риски.

## Flutter и Dart

- Соблюдай версию SDK и правила из `pubspec.yaml`; не повышай минимальную версию
  без явной причины.
- Используй sound null safety, `const` там, где это возможно, и неизменяемые
  модели состояния.
- Предпочитай маленькие композиционные `StatelessWidget`/`StatefulWidget`.
  Не помещай бизнес-логику в `build` и не вызывай побочные эффекты из `build`.
- Сохраняй границы слоёв проекта. Если архитектура ещё не выбрана, начни с
  `features/<feature>/{data,domain,presentation}` и не добавляй тяжёлую
  зависимость ради одной страницы.
- Не подавляй предупреждения анализатора без комментария, объясняющего причину.

## Material 3

- Используй `ThemeData` и `ColorScheme` как единый источник цветов, типографики,
  форм и состояний. Для новой темы предпочитай
  `ColorScheme.fromSeed(seedColor: ...)`.
- Не хардкодь цвета, размеры текста и отступы в экранах, если значение является
  частью дизайн-системы. Выноси их в тему или именованные токены.
- Используй актуальные M3-компоненты: `NavigationBar`, `NavigationDrawer`,
  `FilledButton`, `FilledButton.tonal`, `SegmentedButton`, `SearchBar` и т. п.
  Не возвращайся к Material 2-компонентам без совместимости или UX-причины.
- Явно задавай `useMaterial3: true` в корневой теме, если это улучшает читаемость
  проекта; не выставляй `false`.
- Настраивай компонентные темы (`buttonTheme`, `inputDecorationTheme`,
  `snackBarTheme` и др.) централизованно.
- Проверяй контраст, фокус клавиатуры, размер tap target, семантику, порядок
  обхода и работу с увеличенным размером шрифта.
- Для адаптивной вёрстки используй ограничения и `LayoutBuilder`, а не проверки
  конкретной модели устройства. Не допускай переполнений и горизонтального
  скролла без явного UX-решения.

## Состояние, навигация и ошибки

- Состояние загрузки, пустое состояние, ошибка и успешный результат должны быть
  различимы визуально и доступны через semantics.
- Асинхронные операции должны корректно обрабатывать отмену/размонтирование и
  не вызывать `setState` после `dispose`.
- Показывай пользователю понятное сообщение, а технические детали оставляй в
  логах. Не логируй секреты, токены и персональные данные.

## Проверки

```bash
flutter pub get
dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test
```

Для изменений, затрагивающих платформу или сборку, добавь соответствующую
проверку (`flutter build apk --debug`, `flutter build web` и т. д.).

## MCP и внешние источники

Команды подключения и шаблоны конфигурации находятся в
`docs/CODEX_SETUP.md`. Не добавляй ключи и токены в репозиторий. Для актуальной
документации используй подключённый MCP или официальные сайты, а в изменениях
фиксируй конкретную версию SDK/пакета, если она влияет на поведение.

Если вопрос касается OpenAI API, Codex, ChatGPT, plugins или MCP, всегда сначала
используй OpenAI developer documentation MCP, если он подключён.
